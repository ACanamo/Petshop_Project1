**PETCHUP — CTO project audit | 17 September 2026**

**Recommendation: hold production checkout launch until the P0 and P1 findings below are resolved and verified in staging.** The project has a usable storefront foundation, but inventory, order confirmation, and reporting can disagree. This is a source-based engineering assessment, not a live penetration test or a certification of the deployed service.

| Executive dimension | Assessment | Evidence and implication |
| --- | --- | --- |
| Architecture | Suitable for a small storefront | React 18, Vite, React Router, and Supabase; domain contexts and route-level lazy loading provide a workable structure. A rewrite is not the immediate priority. |
| Security | Release blocker | A privileged inventory RPC is explicitly executable by anonymous visitors in the supplied schema. |
| Checkout integrity | Release blocker | Timeout fallback can confirm an order absent from the backend and can deduct inventory a second time. |
| Business reporting | Unreliable for decisions | Revenue sums every cached order, including cancelled, pending, and local-only records. |
| Engineering assurance | Insufficient | Build passes, but no application tests, test/lint scripts, or repository CI workflows were found. Bundled skill tests are unrelated to the application. |
| Operational readiness | Not established | Schema is a single rerunnable SQL file; no versioned migration workflow or operational runbook was found. Live backups, monitoring, and deployment settings were not inspected. |

P0 = immediate containment if deployed; P1 = resolve before real customer transactions; P2 = next delivery cycle. Owners below are suggested responsibilities, not existing team assignments. All defects are confirmed in source; database execution and browser behavior still require staging verification.

| ID / priority | Finding and source evidence | Business impact | Recommended action / suggested owner |
| --- | --- | --- | --- |
| A01 / P0 | `supabase_schema.sql:996–1026`: `deduct_product_stock` runs as SECURITY DEFINER, grants EXECUTE to `anon` and `authenticated`, and has no identity, order, or authorization check. | If deployed with the expected privileged owner and exposed RPC, an unauthenticated caller can reduce publicly listed products to zero stock without buying anything. | Remove client execution and retire the separate deduction path; keep stock changes inside validated order transactions. Verify actual deployed grants immediately. Backend owner. |
| A02 / P1 | `src/context/OrdersContext.jsx:149–210` races checkout against six seconds, then returns a local order. `src/components/cart/CartDrawer.jsx:116–130` deducts stock for that fallback and opens confirmation. `src/context/StoreContext.jsx:423` invokes the separate stock RPC. | Timeout does not establish server failure. A delayed successful checkout can deduct twice; a failed checkout can still display “Order Confirmed” and disappear from the actual merchant queue. | Use a durable idempotency key and server lookup/reconciliation. Preserve an unknown outcome until confirmed; prohibit production local-success fallback and separate stock deduction. Frontend + backend owners. |
| A03 / P1 | `supabase_schema.sql:817–879`: all item quantities are checked before deductions, without combining duplicate product IDs. The products table has no nonnegative-stock CHECK constraint. | With stock 5, two lines for the same product at quantity 4 each both pass; deductions leave stock at -3. | Aggregate or reject duplicates, validate the aggregate, lock products in deterministic order, and enforce nonnegative stock. Backend owner. |
| A04 / P1 | `supabase_schema.sql:1081–1117`: deleting any non-cancelled order restores its items, including delivered orders. `OrdersContext.jsx` exposes individual and bulk deletion. | Removing historical fulfilled orders manufactures available stock and removes transaction history. | Archive orders; only restore stock through an explicit cancellation/return workflow with fulfillment-state checks. Backend + operations owners. |
| A05 / P1 | `src/context/OrdersContext.jsx:9–104` stores all fetched orders under one persistent browser key, merges them indefinitely, and does not clear them at logout. `:323–325` also matches history by email. | Names, emails, and orders remain on a shared browser after sign-out; admin-fetched records remain in storage. Cloud-deleted orders can reappear from stale local copies. This is a local retention issue, not proof of an RLS bypass. | Scope caches by authenticated user, clear sensitive state and open invoices on session changes, use immutable user IDs, and reconcile deletions against the backend. Frontend owner. |
| A06 / P1 | `src/context/CartContext.jsx:43–52` replaces the guest cart with the saved cloud cart at login. Checkout requires login. | A new shopper who adds products and then registers can lose the entire basket when the empty saved cart loads. | Define and implement a guest-to-account cart merge, persist it, and test checkout through signup/login. Frontend owner. |
| A07 / P1 | `src/components/admin/MetricsRibbon.jsx:10` sums all order totals without status or persistence filters. | Cancelled, pending, and local-only orders are counted as “Store Revenue”; management receives inflated figures. | Define order value versus recognized/collected revenue, use authoritative server aggregates, and exclude invalid statuses/local records. Product + backend owners. |
| A08 / P1 | `supabase_schema.sql:614–663` recalculates order totals using catalog prices, but `:851` saves the original client-supplied items JSON. `src/components/orders/InvoiceModal.jsx:151–160` displays the supplied names and prices. | Stale or altered item prices can produce invoice lines that disagree with the authoritative total. The server does protect the aggregate charge calculation. | Construct immutable line-item snapshots on the server using catalog data and quantities, then derive invoices from those snapshots. Backend owner. |
| A09 / P1 | `package.json` contains dev/build/preview only; no application test suite or CI workflow was found. | Checkout and authorization regressions have no automated release gate; a successful bundle does not validate database behavior. | Add staging database access-control and transaction tests plus browser tests for checkout, login/cart preservation, and account switching; run them in CI. Engineering owner. |
| A10 / P2 | `src/context/AuthContext.jsx:39–40` grants frontend admin status by email or app metadata as well as profile role; `supabase_schema.sql:171–176` checks only profile role. `ProtectedRoute.jsx` redirects before initial session restoration has a completion state. | Demoted users may still see admin UI while database actions fail. Direct admin navigation can redirect valid sessions during restoration. This does not itself grant backend admin access. | Use the same role authority on both sides and wait for auth initialization before redirecting. Frontend owner. |
| A11 / P2 | `src/lib/supabase.js:4–5` silently defaults to a concrete shared backend. `supabase_schema.sql:495` repeats an email-based admin promotion whenever the whole script runs. | Missing staging configuration can connect a build to the wrong database; rerunning setup can undo a deliberate admin demotion. The publishable key is not a secret credential. | Require environment-specific production configuration, isolate staging, version migrations, and separate one-time privileged bootstrap from recurring updates. Platform owner. |
| A12 / P2 | `StoreContext.jsx:55`, `OrdersContext.jsx:67`, and browser-side metrics load/process whole result sets without pagination or server aggregation. | Growing datasets increase transfer/render cost; server row caps can yield incomplete catalogs or order metrics. No load benchmark was run. | Add paginated queries, narrow projections, server aggregates, and representative-volume performance checks. Backend + frontend owners. |
| A13 / P2 | `src/context/CartContext.jsx:102–124` awaits upsert/delete but does not inspect returned `{ error }`. Concurrent writes have no sequencing. | Cart changes can silently fail or persist an older quantity, surprising users at their next login. | Inspect API errors, serialize/coalesce writes per cart item, retry safely, and make persistent failures visible. Frontend owner. |
| A14 / P2 | `CartDrawer.jsx`, `InvoiceModal.jsx`, and `OrderSuccessModal.jsx` declare modal dialogs but contain no focus trap, initial focus management, or return-focus handling. | Keyboard focus can escape the open dialog into obscured content. Escape handling and dialog labels are useful existing foundations. | Adopt a shared accessible dialog primitive and verify keyboard navigation and screen-reader behavior. Frontend owner. |

Supabase documents that SECURITY DEFINER executes with the creator's privileges and that function execution grants must be restricted explicitly; these semantics underpin A01. See [Database Functions](https://supabase.com/docs/guides/database/functions). Access-control release tests should exercise both grants and ownership policies, as described in [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security).
